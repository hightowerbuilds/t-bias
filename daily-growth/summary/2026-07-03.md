# Session Summary — 2026-07-03

Pivot day: decided to rebuild t-bias from scratch on **Deno Desktop**, scorched the old
Tauri/Rust app, and stood up a working Phase 0 spine.

## What We Did

### 1. Codebase Review
Walked the existing app end to end (Tauri 2 + Rust PTY backend, SolidJS frontend, xterm.js
terminal). Confirmed the memory note was stale — the terminal had already migrated off the
custom canvas VT parser to xterm.js. Identified `pty.rs` (process lifecycle, signal handling,
`proc_pidinfo` cwd/foreground tracking) as the crown jewel worth carrying forward.

### 2. Rebuild Decision + Research
Verified (via web research, since it's recent) that **Deno Desktop** is real — shipped in
**Deno 2.9** (June 2026): `deno desktop` CLI, native WebView backend (~68MB vs ~309MB CEF),
`Deno.BrowserWindow`/`window.bind()` in-process bindings, auto-detects SolidStart/TanStack
Start/Vite, `Deno.autoUpdate()`.

**Locked the stack:**
- Deno Desktop shell (native WebView)
- Vite + SolidJS **SPA** (not SSR — no benefit for a local app)
- TanStack Router + TanStack Query
- xterm.js + WebGL (carried over)
- **Rust PTY sidecar** reusing `pty.rs` (not pure-Deno FFI)
- `node:sqlite` + Drizzle ORM
- tinykeys for hotkeys
- Optional AI (Anthropic SDK, server-side in Deno) — Phase 6

**Key call — PTY strategy.** Deno has no native PTY (`Deno.Command` gives pipes, not a
controlling TTY). Corrected an early lean toward raw-libc FFI: FFI is a *mechanism*, not a
language choice, and terminal perf is bottlenecked by xterm.js/WebGL rendering, not PTY
transport. So the PTY layer optimizes for correctness → **reuse `pty.rs` as a Rust sidecar**.

### 3. Roadmap
Wrote `daily-growth/roadmaps/deno-rebuild-roadmap.md` — a living plan: goal, locked stack,
runtime architecture diagram, open questions, phased build order (0–6), risks, decisions log.
Build order deliberately front-loads the risky PTY streaming path in Phase 1.

### 4. Scorched Earth
`git rm` of the entire old app — `src/`, `src-tauri/`, build config, and a `node_modules/`
that had been committed (3,298 deletions). Preserved reuse material to scratchpad seeds:
- `rust-pty-seed/` — `pty.rs`, `shell_registry.rs`, `session.rs`, `fs_ops.rs`, `config.rs`
- `frontend-seed/` — `pane-tree`, `workspace-state`, `session-state`, canvas, editor,
  prompt store, `XtermHost`
(Everything also recoverable from git history.)

### 5. Phase 0 — Scaffold (complete)
Upgraded Deno 2.7.11 → **2.9.1** (`brew upgrade deno`; the brew build has `deno upgrade`
disabled). Empirically probed the desktop runtime — confirmed `deno desktop <entry>` *builds*
an `.app` via the laufey webview backend (v0.5.0), globals injected only under that runtime.

**Built the app spine:**
- SolidJS SPA (Vite 8, solid 1.9): TanStack Router (1.170) with Home/Terminal routes,
  TanStack Query (5.101), tinykeys (4.0)
- `main.ts` — Deno entrypoint that serves the built `dist/` plus the backend bridge:
  `GET /api/ping` (HTTP) and `WS /ws` (echo now; **PTY output stream reuses it in Phase 1**).
  Guarded `BrowserWindow` block so the same file runs as a browser web app *and* a native shell.

**Dev workflow established:** develop as a normal web app (`deno task serve` → browser,
fast), `bun run build` rebuilds the SPA, `deno task desktop` bundles the native `.app`.
